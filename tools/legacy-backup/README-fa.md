# ابزار پشتیبان‌گیری از نصب‌های قدیمی MedPad (legacy-backup)

این ابزار برای وقتی است که **روی یک نصب قدیمی MedPad (بدون قابلیت پشتیبان‌گیری) اطلاعات وارد کرده‌اید** و می‌خواهید همان داده‌ها را به نصب جدید (v1.9.14-dev.2 و بالاتر) منتقل کنید:

```
پایگاه‌دادهٔ قدیمی (medpad.db)  →  این ابزار  →  فایل JSON پشتیبان  →  بازگردانی در اپ جدید
```

خروجی ابزار دقیقاً همان قالبی است که خود برنامه برای «خروجی پشتیبان (JSON)» می‌سازد و همان مسیر «بازگردانی از فایل پشتیبان (JSON)» آن را می‌خواند.

- **بدون نیاز به نصب چیزی:** فقط پایتون ۳ (نسخهٔ ۳.۸ یا بالاتر)؛ هیچ کتابخانهٔ جانبی لازم نیست.
- **بدون تغییر در فایل اصلی:** ابزار روی یک کپی موقت از فایل کار می‌کند؛ فایل اصلی شما فقط خوانده می‌شود.
- **پشتیبانی از همهٔ نسخه‌های ساختار:** v4 تا v14 (هر نسخه‌ای که تا امروز منتشر شده). ستون‌هایی که در نسخهٔ قدیمی وجود نداشته‌اند، دقیقاً با همان مقادیر پیش‌فرضی پر می‌شوند که مسیر مهاجرت خود برنامه استفاده می‌کند.
- **فایل wal.:** اگر کنار فایل، `medpad.db-wal` هم باشد (آخرین تغییراتی که هنوز در فایل اصلی «تسویه» نشده‌اند)، ابزار خودش می‌یابد و آن تغییرات هم در خروجی می‌آیند.

---

## ۱) گرفتن فایل پایگاه‌داده از دستگاه قدیمی (سه مسیر)

نام پکیج برنامه: `com.medpad.tracker` — نام فایل پایگاه‌داده: `medpad.db`

مسیر کامل روی دستگاه: `/data/data/com.medpad.tracker/databases/medpad.db`

### مسیر الف — `adb backup` (اگر نسخهٔ قدیمی اجازهٔ بکاپ سیستمی داده باشد)

از نسخه‌های `1.9.12` به بعد `allowBackup` روشن است ولی قواعد P10 پایگاه‌داده را از **بکاپ ابری** خارج کرده‌اند؛ برای بکاپ محلی `adb` همین قواعد اعمال می‌شوند، بنابراین این مسیر **فقط روی نسخه‌های قدیمی‌تر (پیش از P10) یا اگر خروجی سالم بود** جواب می‌دهد — امتحانش ارزش دارد:

```bash
adb backup -f medpad.ab com.medpad.tracker
# روی دستگاه تأیید کنید (بدون رمز = «don't use password»)
```

خروجی `.ab` یک آرشیو tar با هدر ۲۴-بایتی است. استخراج:

```bash
dd if=medpad.ab bs=24 skip=1 | zlib-flate -uncompress > medpad.tar   # یا با busybox/abe
tar xvf medpad.tar
# فایل در: apps/com.medpad.tracker/db/medpad.db
```

(ابزار آمادهٔ «Android Backup Extractor (abe)» هم همین کار را با یک دستور می‌کند.)

### مسیر ب — دستگاه root شده (مطمئن‌ترین مسیر)

```bash
adb shell su -c "cat /data/data/com.medpad.tracker/databases/medpad.db"   > medpad.db
adb shell su -c "cat /data/data/com.medpad.tracker/databases/medpad.db-wal" > medpad.db-wal   # اگر وجود داشت
```

دو فایل را در **یک پوشه** بگذارید (اسم `wal` باید دقیقاً `medpad.db-wal` باشد) تا ابزار هر دو را بخواند.

> نکته: اگر `su` روی دستگاه شما قابل استفاده نیست، با یک فایل‌منیجر root (مثل MiXplorer با دسترسی روت) کل پوشهٔ `databases` را کپی کنید.

### مسیر ج — فایل .db از بکاپ‌ها یا فایل‌منیجر

هر فایل `medpad.db` سالمی که از قبل دارید (کپی دستی، بکاپ TWRP/Titanium، فایل‌منیجر دارای دسترسی روت و…) مستقیماً قابل استفاده است. اگر کنارش `medpad.db-wal` هم دارید، هر دو را در یک پوشه بگذارید.

> **چرا به‌روزترین گزارش‌ها ممکن است نباشند؟** SQLite گزارش‌های تازه را اول در فایل `wal` می‌نویسد. اگر فقط فایل اصلی را برداشته‌اید و فایل `wal` کنارش نبوده، گزارش‌های چند ساعت/چند روز آخر ممکن است در فایل اصلی نباشند. اگر برنامهٔ قدیمی هنوز نصب است، قبل از برداشتن فایل، یک بار برنامه را باز و ببندید (تسویهٔ wal) یا هر دو فایل را با هم بردارید.

## ۲) اجرای ابزار

```bash
python3 medpad_legacy_backup.py medpad.db
# یا با مسیر خروجی دلخواه:
python3 medpad_legacy_backup.py medpad.db -o MedPad-Backup-OldPhone.json
```

خروجی پیش‌فرض کنار فایل ورودی ساخته می‌شود: `medpad.db-backup.json`

## ۳) بازگردانی در اپ جدید

1. فایل JSON را به گوشی جدید منتقل کنید (تلگرام/کیبل/هر روشی).
2. MedPad جدید → صفحهٔ اصلی → دکمهٔ **«حساب کاربری»** (آیکون شخص، بالا) → بخش **«پشتیبان‌گیری و بازگردانی»**.
3. **«بازگردانی از فایل پشتیبان (JSON)»** را بزنید و فایل را انتخاب کنید.
4. گزارش فارسیِ «افزوده / به‌روزرسانی / ردشده» را جدول‌به‌جدول می‌بینید.

**مهم:**
- بازگردانی **ادغامی** است — هیچ داده‌ای از دستگاه جدید حذف نمی‌شود.
- پیش از هر بازگردانی، برنامه به‌طور خودکار از وضعیت فعلی **نسخهٔ ایمنی** می‌گیرد (۳ نسخهٔ آخر نگه داشته می‌شود؛ قابل مشاهده و بازگردانی از «نسخه‌های ایمنی» در همین بخش).
- اگر ترجیح می‌دهید فایل `.db` را مستقیم (بدون تبدیل با رایانه) وارد کنید، همان بخش گزینهٔ **«بازگردانی از پایگاه‌داده قدیمی (.db)»** را دارد — فایل `.db` قدیمی را انتخاب کنید؛ برنامه خودش نسخهٔ ساختار را تشخیص داده و ارتقا می‌دهد.

## ۴) انتقال صداهای ضبط‌شده

فایل JSON فقط **مسیر** فایل‌های صوتی را نگه می‌دارد، نه خود فایل‌ها. مسیرها روی دستگاه قدیمی چیزی مثل این است:

```
/data/user/0/com.medpad.tracker/files/voice/<uuid>.m4a
```

روی دستگاه جدید، همان پکیج نصب است، پس مسیر مقصد **دقیقاً همین** است. برای منتقل کردن (نیازمند دسترسی root یا `adb` با دسترسی):

```bash
# کل پوشهٔ صوت‌ها را از گوشی قدیمی بردارید:
adb shell su -c "tar cf - -C /data/data/com.medpad.tracker/files voice" | tar xf -
# و به گوشی جدید برگردانید (برنامه در حال اجرا نباشد):
adb shell su -c "tar xf - -C /data/data/com.medpad.tracker/files" < voice.tar
```

اگر گوشی جدید root نیست، این صوت‌ها فقط زمانی قابل پخش‌اند که با همان مسیر مطلق در جای خود باشند؛ در غیر این صورت گزارش‌ها بدون صوت بازگردانی می‌شوند (خود برنامه با نبودن فایل، بی‌صدا و بدون خطا ادامه می‌دهد).

## ۵) قرارداد قالب JSON (formatVersion 1)

```json
{
  "manifest": {
    "app": "MedPad",
    "formatVersion": 1,
    "schemaVersion": 14,
    "exportedAt": "2026-11-03T12:00:00Z",
    "appVersion": "medpad-legacy-backup/1.0",
    "sourceSchemaVersion": 11,
    "sourceDb": "medpad.db"
  },
  "entities": {
    "doctors": [ { "id": "...", "name": "...", "lat": 35.7, "lng": 51.4, "...": "..." } ],
    "customer_links": [], "customer_profiles": [], "pending_customer_ops": [],
    "pending_checkins": [], "pending_locations": [],
    "planned_visits": [], "op_events": []
  }
}
```

- کلیدها همان **نام ستون‌های SQLite** هستند (که با نام فیلدهای کاتلین یکی‌اند).
- مقادیر تهی **نوشته نمی‌شوند** (کلید حذف می‌شود)؛ خوانندهٔ برنامه هم کلید گم‌شده و `null` صریح را یکسان می‌فهمد.
- بولین‌ها به‌صورت `true/false` نوشته می‌شوند؛ ستون‌های `uid` (کلیدهای خودافزای محلی) هرگز جزو قالب نیستند — هویت پایدار ردیف‌ها `id`/`customerId` و کلید idempotency یعنی `localId` است.
- منطق ادغام در برنامه:
  - `doctors` بر اساس `id` با قاعدهٔ آخرین‌نوشته (`updatedAt`)
  - `customer_profiles` بر اساس `customerId` با قاعدهٔ آخرین‌نوشته (`fetchedAt`)
  - `customer_links` و `planned_visits` بر اساس `id` (جایگزینی — آینهٔ فقط‌خواندنی سرور)
  - چهار صف آفلاین بر اساس `localId` بدون تکرار (همان کلیدی که سرور هم به آن اعتماد می‌کند)

نمونهٔ خروجی واقعی: خروجی خود برنامه («خروجی پشتیبان (JSON)») را بگیرید و ببینید.

## ۶) تست ابزار

```bash
python3 -m unittest test_legacy_backup.py -v
```

تست‌ها فایل‌های فیکسچر (نسخه‌های v6/v11/v13/v14 و فایل خراب) را می‌سازند و خروجی را با خروجی موردانتظار مقایسه می‌کنند. نیازی به اینترنت یا کتابخانهٔ جانبی ندارند.

## ۷) محدودیت‌ها (صادقانه)

- ساختارهای **زیر v4** پشتیبانی نمی‌شوند (قبل از اولین نسخهٔ منتشرشدهٔ مخزن؛ در عمل وجود ندارند).
- صوت‌ها و عکس‌ها داخل JSON منتقل نمی‌شوند (بخش ۴).
- ابزار روی نسخه‌های ساختار **جدیدتر از v14** (نسخه‌های آینده) تا به‌روزرسانی‌شدن جدول نگاشت، کار نمی‌کند و صادقانه خطا می‌دهد.
